## 优化代码（分步重构法）

适用场景：代码经过多次迭代后质量下降，需要系统性地诊断和重构。

核心思路：**先诊断，再分批清理，最后验证**，避免一次性大改引入风险。

### 第一步：诊断——让模型先审查，不要急着改

```markdown
## 请审查以下代码，不要修改，只做诊断

这段代码经过多次迭代修改，目前功能正常但代码质量下降。请逐一列出以下问题：

1. **死代码**：不再被调用的函数、变量、导入
2. **兼容/过渡代码**：为兼容旧逻辑而保留但已不需要的代码（如旧接口适配、废弃的 fallback 逻辑）
3. **重复逻辑**：多处实现了相同或相似功能的代码段
4. **风格不一致**：命名风格混乱、缩进不统一、注释与代码矛盾
5. **过度复杂**：可以简化但因为迭代叠加而变复杂的逻辑
6. **潜在 bug**：迭代过程中可能引入的逻辑矛盾或边界问题

对每个问题：
- 指出具体位置（行号或代码片段）
- 说明为什么它是问题
- 标注严重程度（高/中/低）

代码如下：
（粘贴代码）
```

### 第二步：清理——按优先级逐步重构

拿到诊断结果后，不要一次全改，按优先级分批处理：

#### 第一批：删（风险最低）

```markdown
根据上面的诊断结果，请执行以下清理：

1. 删除所有未使用的 import / 变量 / 函数
2. 删除被注释掉的旧代码
3. 删除已确认不再需要的兼容代码（列出你认为可以安全删除的，我来确认）

要求：
- 不改变任何现有功能和逻辑
- 每删除一处，用注释标注 `// [REMOVED] 原因`（最终版本再去掉这些注释）
```

#### 第二批：合（提取重复）

```markdown
请合并/提取重复逻辑：

1. 将重复的代码提取为公共函数
2. 统一相似功能的不同实现，保留更好的那个
3. 保持函数签名和对外接口不变

对每处合并，说明：
- 合并了哪些地方
- 为什么选择保留这个版本
```

#### 第三批：理（结构与风格）

```markdown
请统一代码风格和结构：

1. 统一命名风格（全部使用 camelCase / snake_case）
2. 理清函数顺序（公共方法在前，私有方法在后 / 按调用顺序排列）
3. 补充或修正关键注释（删除过时注释，补充缺失的关键逻辑说明）
4. 简化过度复杂的逻辑

不要改变功能行为。
```

### 第三步：验证

```markdown
请对比重构前后的代码：

1. 用表格列出所有改动点及改动原因
2. 确认所有公开接口（函数签名、入参、返回值）未发生变化
3. 列出需要重点回归测试的场景
4. 是否存在任何行为变化的风险？如有请明确指出
```
